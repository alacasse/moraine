# Policy engines and closest open-source overlaps

Research snapshot: 2026-09-20. Scope: a Python, model/framework/MCP-independent action gate returning allow, deny, or approval required. This is a source investigation, not a security audit or a tested adoption recommendation. No packages were installed or executed. Primary documentation and selected implementation files were read; implementation links are pinned where practical.

## Finding

**A generic three-way Python tool gate is already implemented by multiple projects.** Hexgate is the closest direct product overlap; apparitor is the closest small, engine-neutral authorization integration. Microsoft Agent Governance Toolkit already has a concrete action-bound approval coordinator, although its inspected Python module explicitly says it is not yet integrated into the policy evaluator or legacy handlers. The strongest next step is a small adoption/contribution experiment against these projects before starting another gate library. This conclusion is an inference from the evidence below, not a claim that any one project meets every proposed requirement.

## 1. Hexgate — closest direct comparison

- **License / deployment:** MIT; Python SDK with local policy and no platform requirement. Optional hosted or self-hosted platform. Framework adapters cover OpenAI Agents, LangChain, Google ADK and Pydantic AI. [Repository](https://github.com/HexamindOrganisation/hexgate), [license](https://github.com/HexamindOrganisation/hexgate/blob/da41aa76e7e6a4a570976a3e9e0a5cd509dc3f54/LICENSE).
- **Actual core:** `PolicyEnforcer.decide(tool_name, arguments)` delegates to a `PolicyEngine` protocol and returns a typed `Decision`; the outcome enum is `allow`, `deny`, `needs_approval`. Current source supports role, arguments, contextual attributes and run facts. Both Pydantic policy and compiled Rego/WASM implementations fit the same protocol. [Enforcer](https://github.com/HexamindOrganisation/hexgate/blob/da41aa76e7e6a4a570976a3e9e0a5cd509dc3f54/hexgate/security/enforcer.py), [decision / engine protocol](https://github.com/HexamindOrganisation/hexgate/blob/da41aa76e7e6a4a570976a3e9e0a5cd509dc3f54/hexgate/security/decision.py).
- **Enforcement:** adapters replace callable tools. The inspected OpenAI adapter wraps `FunctionTool.on_invoke_tool`, sending the call through a shared runner; that runner applies pre-guards before policy evaluation, then approval if needed, then invokes the tool. This is implemented plumbing, not only a README promise. [Adapter](https://github.com/HexamindOrganisation/hexgate/blob/da41aa76e7e6a4a570976a3e9e0a5cd509dc3f54/hexgate/adapters/openai/tools.py), [runner](https://github.com/HexamindOrganisation/hexgate/blob/da41aa76e7e6a4a570976a3e9e0a5cd509dc3f54/hexgate/guards/runner.py).
- **Approval limits:** implementation accepts a boolean or sync/async callback and coerces callback results to bool. The docs explicitly leave timeout handling to the developer and report no cross-process durability or approver-role authorization. A missing handler blocks. Thus it supplies a real execution gate but not a durable, authenticated, exact-action approval protocol. [Approval implementation](https://github.com/HexamindOrganisation/hexgate/blob/da41aa76e7e6a4a570976a3e9e0a5cd509dc3f54/hexgate/agents/approvals.py), [approval documentation](https://docs.hexgate.ai/concepts/approval-required), [decision behavior](https://docs.hexgate.ai/concepts/policy-decision).
- **Delegation / trust caution:** current source combines the caller's roles by permissive union: an allow from one role overrides another role's approval requirement. That is role aggregation, not the intersection required for attenuating delegated authority. The enforcer explicitly describes contextvar attributes as spoofable within the process. Docs describe per-user Biscuit context and optional expiry, but authenticating the caller remains the host's responsibility. They warn that incorrectly scoped streaming loses the user role and falls back to default policy. [Role combination](https://github.com/HexamindOrganisation/hexgate/blob/da41aa76e7e6a4a570976a3e9e0a5cd509dc3f54/hexgate/security/decision.py), [context handling](https://github.com/HexamindOrganisation/hexgate/blob/da41aa76e7e6a4a570976a3e9e0a5cd509dc3f54/hexgate/security/enforcer.py), [user scope](https://docs.hexgate.ai/concepts/user-scope).

**Contribution experiment:** use the existing standalone enforcer and one wrapper with the proposed action scenarios. Determine whether authenticated approval identity, immutable action binding, expiry/revalidation and a durable store belong upstream. Do not assume its documented Biscuit mechanism proves a complete transitive delegation chain. Direct credentials or an unwrapped callable remain an alternate execution route unless the deployment removes them. The last sentence is a boundary inference from the wrapper design.

## 2. apparitor — strongest small authorization integration

- **License / Python:** Apache-2.0, Python >=3.10, beta. The core depends on HTTPX and Pydantic; framework adapters and Cedar are optional extras. The README identifies a solo-maintained project and an independent external security review as pending. [Project metadata](https://github.com/jhawlwut/apparitor/blob/cb64c26497ca90167409d59d5e49d222965e07e2/pyproject.toml), [repository](https://github.com/jhawlwut/apparitor).
- **Core / policy reuse:** an adapter-independent `AuthorizationEngine` normalizes tool calls, maps identity/action/resource/context, evaluates a backend, and returns a verdict. OPA's Data API, in-process Cedar through `cedarpy`, and AuthZEN are supported; OpenFGA through AuthZEN is described as experimental. Native OPA here means a native Data API integration, not an embedded OPA interpreter. [Engine](https://github.com/jhawlwut/apparitor/blob/cb64c26497ca90167409d59d5e49d222965e07e2/src/apparitor/engine.py), [backend matrix](https://github.com/jhawlwut/apparitor#what-apparitor-connects).
- **Identity / scope:** request-scoped host identity, verified OAuth subject in the FastMCP adapter, and dual-principal mapping requiring user and agent checks to allow. Arguments are available to policy as untrusted resource attributes. Failures map to block or human review; a review predicate cannot turn a deny into allow. [Requirements](https://github.com/jhawlwut/apparitor/blob/cb64c26497ca90167409d59d5e49d222965e07e2/docs/requirements.md), [mapping](https://github.com/jhawlwut/apparitor/blob/cb64c26497ca90167409d59d5e49d222965e07e2/src/apparitor/mapping.py).
- **Human review is not an approval service:** the FastMCP source explicitly refuses `HUMAN_REVIEW`; it exposes a distinct error so the host can escalate. It neither pauses for a human nor supplies approval storage, identity verification, binding or resume. The host must deploy middleware on every applicable server; mounted servers are covered only when traffic traverses the parent. Source also documents list-filtering limits. [FastMCP implementation](https://github.com/jhawlwut/apparitor/blob/cb64c26497ca90167409d59d5e49d222965e07e2/src/apparitor/fastmcp.py).

**Contribution experiment:** integrate an existing policy engine and put the gate at an unavoidable tool server. Add a bounded approval mechanism or execution adapter if maintainers want it. This avoids inventing a policy language. Its narrow scope and small dependency core fit the proposed library better than a full governance platform, but maturity and maintainer capacity need assessment.

**Native OPA approval limitation:** the inspected `OPABackend` accepts boolean rule results and supplies no advisory context, so its `review_predicate` path does not apply. An experiment using that backend needs an explicit broker-side approval classification after authorization, or a separately agreed AuthZEN review mapping. Do not infer that OPA's ability to return arbitrary JSON means this particular adapter supports those responses. [Pinned backend implementation](https://github.com/jhawlwut/apparitor/blob/cb64c26497ca90167409d59d5e49d222965e07e2/src/apparitor/backends.py).

## 3. Microsoft Agent Governance Toolkit — concrete approval protocol, integration gap

The accepted ADR specifies a durable approval request, action digest, policy and chain versions, authenticated approvers, expiry, execution-time revalidation and one-time consumption. It also candidly documents older unbound webhook payloads and differing legacy approval behavior. An accepted ADR alone is not implementation evidence. [ADR 0030](https://github.com/microsoft/agent-governance-toolkit/blob/e7f5d2bafca79e508e80a8cd7e0a6f0bb05ce197/docs/adr/0030-action-bound-approval-protocol.md).

The Python `approval_protocol` package does exist under MIT. Its module documentation says it is the additive first migration step and is **not yet wired into the policy evaluator or legacy approval handlers**. The coordinator checks stages, builds linked entries, checks action/policy/chain equality and expiry, and calls a store's atomic consume method before returning allowed. Only the inspected in-memory reference store is supplied by that package; a production backend implements the store protocol. [Package status](https://github.com/microsoft/agent-governance-toolkit/blob/e7f5d2bafca79e508e80a8cd7e0a6f0bb05ce197/agent-governance-python/agent-mesh/src/agentmesh/governance/approval_protocol/__init__.py), [coordinator](https://github.com/microsoft/agent-governance-toolkit/blob/e7f5d2bafca79e508e80a8cd7e0a6f0bb05ce197/agent-governance-python/agent-mesh/src/agentmesh/governance/approval_protocol/coordinator.py), [store](https://github.com/microsoft/agent-governance-toolkit/blob/e7f5d2bafca79e508e80a8cd7e0a6f0bb05ce197/agent-governance-python/agent-mesh/src/agentmesh/governance/approval_protocol/store.py).

`submit_entry` accepts identity, roles and identity-assurance arguments supplied by its caller; the inspected function checks identity/role authorization but does not authenticate an OIDC assertion itself. Therefore a trusted transport/host must establish those facts. `validate_for_execution` consumes approval separately from the actual external effect; the integration still owns idempotency and effect execution. These are source-derived integration responsibilities, not claims of an exploitable vulnerability.

**Contribution opportunity:** wiring this existing protocol into one execution path, adding durable storage and validating authenticated approver transport may be more valuable than creating a competing approval schema. Repository breadth and legacy integration complexity are the tradeoff.

## 4. PermitRail — useful exact-action approval comparator, TypeScript

Apache-2.0 TypeScript packages provide policy, approval providers, signed proofs and receipts. The documented action binding covers subject, audience, purpose and optionally an input hash; the embedded gateway consumes proofs before executing a callback. A shared replay guard and durable audit sink are operator responsibilities. Multi-agent chain IDs correlate receipts; they should not be equated with mathematically enforced attenuation of delegated rights. [Repository](https://github.com/chokonaira/permitrail), [production guidance](https://github.com/chokonaira/permitrail/blob/main/docs/production.md), [threat model](https://github.com/chokonaira/permitrail/blob/main/docs/threat-model.md).

The standalone MCP interface is substantially weaker than a credential-holding execution broker: its documented loop asks the agent to authorize, obtain proof, authorize again, then separately call the sensitive tool. The server does not execute that downstream tool or issue its execution receipt; receipts belong to embedded `execute()`. Merely installing this MCP server does not close a direct-call bypass. The docs expose a development-only approval tool that must not serve as the production approval channel. No Python implementation was established in this investigation. [MCP contract](https://github.com/chokonaira/permitrail/blob/main/docs/mcp.md).

## Existing policy engines already cover the decision component

AuthZEN Authorization API 1.0 is a finalized interoperability boundary between policy decision and enforcement components. It standardizes subject/action/resource/context requests and a boolean decision with optional context; it does not standardize a durable human-approval workflow. Policy language and state management are out of scope. Consequently, apparitor's human-review outcome is an integration-level extension, not a third native AuthZEN decision. [OpenID specification, sections 2 and 5.5](https://openid.net/specs/authorization-api-1_0.html).

| Project | Existing relevant capability | Python and deployment | What the application still owns |
|---|---|---|---|
| OPA / Rego | Domain-independent JSON policy decisions; input can carry exact action/context; output can be a custom three-way object, not only a boolean. | Apache-2.0; HTTP works from Python; Go embedding and WASM are other options. | Trusted input, enforcement, approval lifecycle and effect binding. HTTP 200 can contain no `result` for an undefined decision; treat that explicitly. |
| Cedar | Principal/action/resource/context authorization, entity relationships, permit/forbid, diagnostics, schema validation. Default deny; matching forbid overrides permit. | Apache-2.0 Rust core; community `cedarpy` Python binding is explicitly not officially supported by AWS/Cedar. Can operate locally; AWS hosted services are separate. | Native answer is allow/deny. Approval orchestration and delegation representation are application concerns. Policy evaluation errors are skipped by the engine; callers wanting strict deny-on-any-error must inspect diagnostics. |
| OpenFGA | Relationship-based checks, contextual conditions, user/agent/task/resource permission models. Official agent guide includes task/session scope, expiry, call-count conditions and agent binding. | Apache-2.0 server with official Python SDK; self-hosted HTTP/gRPC service. | Check returns authorization, not approval workflow. Host supplies trusted counters/current time, grants/revokes tuples, checks user plus task, and mediates effects. Call-count conditions do not themselves constitute an atomic usage budget. |
| Cerbos PDP | YAML authorization policy over principal/resource/actions and contextual attributes; resource checks and query plans. | Apache-2.0 self-hosted PDP with Python SDK. Cerbos Hub is a separate hosted management plane. | Policy decision integration, authenticated context and durable approvals. Existing MCP authorization examples are already agent integrations. |

Sources: [OPA integration and undefined decisions](https://www.openpolicyagent.org/docs/integration), [OPA repository/license](https://github.com/open-policy-agent/opa), [Cedar semantics](https://docs.cedarpolicy.com/auth/authorization.html), [Cedar repository](https://github.com/cedar-policy/cedar), [cedarpy](https://github.com/k9securityio/cedar-py), [OpenFGA task model](https://openfga.dev/docs/modeling/agents/task-based-authorization), [OpenFGA Python SDK](https://github.com/openfga/python-sdk), [OpenFGA repository](https://github.com/openfga/openfga), [Cerbos repository](https://github.com/cerbos/cerbos), [Cerbos MCP example](https://www.cerbos.dev/blog/dynamic-authorization-for-ai-agents-guide-to-fine-grained-permissions-mcp-servers). The application-responsibility column combines explicit integration requirements with engineering inference; it is not a claim those features could never be built on these engines.

## Agent Control — adjacent, different default failure semantics

Agent Control is Apache-2.0 with a Python SDK, self-hostable server, function decorator and configurable pre/post controls. It supports built-in and custom evaluators; example workflows use observe/deny/steer and manager approval guidance. It is a serious overlap for centrally managed runtime guardrails. [Repository](https://github.com/agentcontrol/agent-control), [steering example](https://github.com/agentcontrol/agent-control/tree/main/examples/steer_action_demo).

However, its inspected `EvaluatorResult` model explicitly requires errors to set `matched=False` and describes that behavior as fail-open. Its steering examples use boolean context such as manager approval. This does not establish a durable authenticated approval protocol or a fail-closed delegated-authorization boundary. Do not substitute its guardrail result for authority without examining SDK/server failure paths and trusted approval provenance. [Control model](https://github.com/agentcontrol/agent-control/blob/9d12df09b680f01f34a48d46de0ad81fbd823ab1/models/src/agent_control_models/controls.py).

## Suggested comparison and remaining uncertainty

Use **apparitor as the first bounded integration experiment** because its small, adapter-independent core reuses policy engines and explicitly separates user and agent permission boundaries. This is an experiment recommendation, not a production endorsement. Compare Hexgate for the proposed Python developer experience and the Agent Governance Toolkit approval module for the narrow exact-action approval contribution. Use PermitRail as a protocol/enforcement contrast, especially its embedded versus standalone-MCP distinction.

The missing proof is practical fit: neither this note nor upstream marketing demonstrates that the proposed app's complete external-effect paths are mediated, that a compromised Python process cannot bypass wrappers, or that approvals survive crashes and concurrent retries correctly in a production integration. Those are deployment and lifecycle requirements worth testing. They are not evidence that a new policy engine is needed.

# Identity, MCP, and human-approval source notes

Checked 2026-09-20. Primary documentation was opened and read; this is a capability/boundary comparison, not an implementation security audit. Versioned MCP sources below use **2026-07-28**, not the older 2025-11-25 revision. Repository documentation on moving branches is a dated observation, not a pinned release guarantee.

## Findings that most affect the project hypothesis

1. **Identity, tool authorization, and approval workflows already have substantial implementations.** A three-way decision enum and tool wrapper are not a sufficient novelty claim.
2. **Approval is not inherently authorization.** Pydantic AI explicitly documents a client-history boundary that permits a client to manufacture its own approved call. An executor must authenticate callers and enforce action permissions independently.
3. **MCP now standardizes much of approval/resume integrity.** Its multi-round-trip mechanism requires integrity protection when returned state affects authorization, recommends principal/action/expiry binding, and explicitly requires server-side enforcement where single use matters.
4. **Credential ownership is decisive.** A cooperative approval SDK can be skipped by an agent with direct downstream credentials. A gateway can enforce policy only if alternate execution and credential access are excluded. These are engineering conclusions from the documented boundaries below.

## Microsoft Entra Agent ID and Agent 365

**Current status:** Microsoft records Agent ID platform general availability under April 2026. Agent 365's overview, updated 2026-08-20, states commercial general availability from 2026-05-01. Do not call both products merely previews; individual integrations/features can still have different status. [Entra announcements](https://learn.microsoft.com/en-us/entra/fundamentals/whats-new#april-2026), [Agent 365 overview](https://learn.microsoft.com/en-us/microsoft-agent-365/overview).

Agent ID supplies identities, blueprint relationships, authentication, access policy, risk controls, lifecycle governance, and auditability for agents, including agents built outside Microsoft. Agent 365 combines enterprise agent management with Entra, Purview information protection/DLP, and Defender threat protection. This is considerably broader than an identifier registry. It is a commercial enterprise ecosystem, not a standalone framework-independent Python authorization primitive. [Agent ID overview](https://learn.microsoft.com/en-us/entra/agent-id/what-is-microsoft-entra-agent-id), [Agent 365 overview](https://learn.microsoft.com/en-us/microsoft-agent-365/overview).

Agents use delegated Graph permissions for acting on behalf of users or application permissions for autonomous service access. Certain high-risk permissions are blocked; ordinary permissions such as `Mail.Read` remain available. **Inference:** a valid agent identity and mailbox-read permission do not themselves restrict the model to five selected messages or approve a particular recipient/body/attachment. Those constraints require a resource service, filtering adapter, policy, or complementary data-protection control. [Agent ID authorization](https://learn.microsoft.com/en-us/entra/agent-id/authorization-agent-id).

Access packages can be requested by an agent or sponsor, routed to approvers, and expire. Sponsors oversee lifecycle/access; they are not evidence that a human approved every future action. **Distinction:** this is human approval of an entitlement assignment, rather than a universal exact-action approval protocol. Conditional Access adds contextual/risk checks. [Governing agent identities](https://learn.microsoft.com/en-us/entra/id-governance/agent-id-governance-overview).

## MCP authorization and security

The 2026-07-28 authorization specification remains an **optional HTTP transport authorization mechanism** using OAuth. The MCP server is a resource server; the client acts for a resource owner. STDIO uses a different credential environment. Servers must validate token audience, reject invalid/expired credentials, and must not accept/transit tokens intended for another resource. OAuth scope challenges support obtaining needed permissions; they are not automatically approval of a concrete transaction. [Authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization).

The security guidance explicitly forbids token passthrough. Its concrete confused-deputy example involves an MCP OAuth proxy, a shared upstream client ID, dynamic downstream registration, and reuse of upstream consent. Required mitigations include **per-user, per-client consent**, exact redirects, and protected, short-lived, single-use OAuth state. This is distinct from merely displaying a tool confirmation. SSRF and downstream resource access still need controls. [Security best practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices).

The current tools specification permits `input_required` results followed by retries carrying `inputResponses` and `requestState`. It calls for input validation and proper access controls; tool annotations from untrusted servers are untrusted. Its stateful-tool guidance says an authenticated resource handle is a **name, not a capability**, and the server should authorize it on every call. **Inference:** hiding an unapproved tool from discovery does not replace checking direct calls. [Tools specification](https://modelcontextprotocol.io/specification/2026-07-28/server/tools).

**Important existing primitive:** multi-round-trip requests treat client-returned `requestState` as attacker controlled. If it affects authorization/resource access/business logic, servers **must** protect integrity, for example with HMAC or AEAD, and reject invalid state. They **should** bind the authenticated principal, short expiry, and originating method plus a digest of salient parameters. The spec explicitly says those checks do **not** guarantee single use; when required, single use **must** be enforced server-side. Thus integrity, action binding, and replay are already specified concerns, not a newly discovered gap. A trusted approval channel is still needed if the MCP client itself is potentially compromised. [Multi-round-trip requests](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr).

## Approval and authorization integrations

| System | Existing boundary | What still belongs to the application |
|---|---|---|
| Pydantic AI | Defers tools based on arguments/context; resumes approvals or denials by call ID | Trusted approval identity/state, resource authorization, grants, credential isolation |
| LangChain/LangGraph | Middleware pauses before execution; checkpointed approve/edit/reject/resume | Approval endpoint authorization, grant/policy evaluation, idempotent execution |
| FastMCP | Server-side component authorization, authenticated claims, filtering and call checks | Domain semantics, delegated-grant store, approval state and adapter-specific execution |
| OpenAI Responses MCP | API approval item before sharing data with remote MCP tool | Human authentication, policy/grant decisions, server-side authorization |

**Pydantic AI:** `requires_approval`, dynamic `ApprovalRequired`, and `DeferredToolRequests/Results` already cover conditional human review. Approval records include tool name, validated arguments, and call ID; `ToolApproved` can override arguments. The documentation explicitly warns that UI adapters accept client-supplied history/approval without a server-side issued-call record: a client can submit its own fabricated approved call. It recommends endpoint authentication and authorization inside the sensitive tool function. That warning applies to any endpoint accepting client-supplied history. This is a strong source for separating a model-level pause from a malicious-client security boundary. [Deferred tools](https://pydantic.dev/docs/ai/tools-toolsets/deferred-tools/#human-in-the-loop-tool-approval).

**LangChain/LangGraph:** human-in-loop middleware examines model tool calls before execution; configured calls pause for approve/edit/reject, with checkpoint persistence. It supplies usable workflow mechanics rather than delegated-authority semantics. LangGraph resumes by restarting the interrupted node, so code before the interrupt executes again; its guidance therefore emphasizes consistent interrupt ordering and recommends idempotent pre-interrupt effects. Application implication: approving a request must not accidentally resend an email on workflow replay. [Human-in-the-loop middleware](https://docs.langchain.com/oss/python/langchain/human-in-the-loop), [Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts).

**FastMCP:** callable checks return allow/deny using authenticated token claims, component metadata, or external systems; checks compose with AND. Its `AuthMiddleware` filters listings and checks execution/resource reads. The documented OAuth-based authorization is skipped for STDIO, so choosing STDIO does not automatically give the same boundary. The tool can use verified token context for domain checks. This is a sensible existing Python integration seam, without inventing a protocol. [Server authorization](https://gofastmcp.com/servers/authorization), [AuthMiddleware](https://gofastmcp.com/python-sdk/fastmcp-server-middleware-authorization).

Permit's existing FastMCP middleware also demonstrates mapping methods/tools to resource/action checks and flattening tool arguments into policy attributes. Its documented deployment requires a Permit account and PDP; a locally running PDP is not evidence that the entire service is an independent OSS stack. Useful evidence that argument-aware policy integration already exists. [Permit/FastMCP integration](https://gofastmcp.com/v2/integrations/permit).

**OpenAI Responses API, not an SDK claim:** official documentation shows a default MCP approval request before sharing data, containing server/tool/arguments, followed by an approval response referencing its request ID. Developers can configure approval behavior. This provides an approval transport; the documentation examined does not establish a general delegated-grant policy model or prove that the responding actor is the human principal. [Official OpenAI MCP documentation](https://developers.openai.com/api/docs/guides/tools-connectors-mcp#approvals).

## Close OSS alternatives worth testing before creating a project

**`monteslu/agentgate` (ISC):** self-hosted REST/MCP gateway that proxies provider credentials, executes reads immediately, queues writes, and offers per-agent service access. It explicitly warns to run separately from agents because an agent with local filesystem access could read its database. This is directly relevant to a personal-assistant boundary. Limits include its broad read/write distinction, explicit trusted-agent write bypass, and service/account access controls rather than a demonstrated portable grant model. Its documentation says service access defaults to all agents. These require deliberate configuration and a domain-specific review; immediate reads can disclose sensitive context. [Repository](https://github.com/monteslu/agentgate), [Write queue](https://github.com/monteslu/agentgate/blob/main/docs/write-queue.md), [Access controls](https://github.com/monteslu/agentgate/blob/main/docs/access-control.md).

**`agentkitai/agentgate` (MIT):** approval service with policies, request store, audit trail, API, SDK/MCP integration, and human channels. Its SDK example leaves downstream execution to caller code after checking approval, so that example alone is cooperative. Newer governance docs describe verified agent IDs, bound API keys, revocation checks and per-agent/tool policy scope. Its policy language is project-specific rather than OPA/Cedar. [Repository](https://github.com/agentkitai/agentgate), [Governance](https://agentkitai.github.io/agentgate/governance.html), [Policies](https://agentkitai.github.io/agentgate/policies.html).

Material limitations in the documentation: MCP tool-call guardrails explicitly **fail open on network/auth errors or absent agent identity**. The policy documentation also warns that flattened request parameters can shadow top-level action/status/urgency. These are reasons to evaluate/contribute before trusting it as the proposed fail-closed boundary, not claims that every deployment is exploitable. [MCP guardrails](https://agentkitai.github.io/agentgate/mcp.html#tool-call-guardrails), [Policy key collisions](https://agentkitai.github.io/agentgate/policies.html#nested-dot-notation-paths).

**SPIFFE/SPIRE:** useful infrastructure when independently deployed agent/executor services need workload authentication. SPIFFE issues short-lived cryptographic workload identities; it is not AI-specific and does not define human delegation, transaction approval, or content filtering. Avoid adopting it merely to give a local proof-of-concept agent an ID. [SPIFFE overview](https://spiffe.io/docs/latest/spiffe-about/overview/).

## Experiment implications — analysis, not new sourced feature claims

The strongest falsifiable experiment is to integrate an existing policy engine with **one credential-owning executor**, using a plain client plus one existing framework adapter. Test a narrowly structured email/draft or mock-payment action, not arbitrary HTTP or shell.

The valuable candidate seam is safe **policy decision → stored pending action → authenticated approval → revalidated execution**, with domain adapters deriving trustworthy resource/disclosure facts. Reuse existing OAuth authentication, policy evaluation, and framework pauses. Approval must bind exact recipients/body/attachment content versions, principal/agent, grant/policy versions, expiry, and execution identity. Recheck current revocation and resource preconditions before execution; changed arguments create a new request. Claim at most once locally with durable state, while handling external timeouts through idempotency or reconciliation rather than pretending a local database makes remote effects exactly once.

Explicit attack cases: fabricated history/approval, modified arguments after approval, mismatched principal, expired/revoked grant, approval reuse, concurrent execution, policy outage, direct downstream credential access, and reading unauthorized source content. If an existing gateway/framework plus small policy adapter handles these cleanly, contribute the adapter and tests. A new enum/models package is not justified by this research alone.
